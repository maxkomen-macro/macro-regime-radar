## GitHub Actions: data-write concurrency and the Git writer

### What's in place

Both `refresh-data.yml` and `intraday-refresh.yml` share a single concurrency group:

```yaml
concurrency:
  group: data-write
  cancel-in-progress: false
```

The two workflows queue against each other instead of racing, which matters because both publish
the DB to the same `data-latest` release asset (serialized so `--clobber` uploads don't race).

The DB is not committed to git: it is downloaded from and uploaded to the `data-latest` Release
(see **Database**). Three workflows write to git, each one generated file:
`refresh-data.yml` (`output/playbook.json`, full mode after a passing validation), `daily-memo.yml`
(`docs/memo/daily_memo.html`) and `weekly-memo.yml` (`docs/memo/weekly_memo.html`).
`intraday-refresh.yml` and `keep-api-warm.yml` never push. The memo workflows are not in the
`data-write` group (they only read the DB).

### The Git writer: `scripts/publish_artifacts.sh` (2026-11-04)

Each writer's commit step sets the bot identity and runs one line:

```yaml
bash scripts/publish_artifacts.sh "Update playbook [skip ci]" output/playbook.json
```

Each attempt (5, with a 5–14 s random backoff) fetches `main`, checks out that exact commit in a
fresh temporary worktree, copies in only the named file (it must be on the script's `ALLOWED`
list), commits there, checks the commit has exactly the fetched `main` as parent and changes only
the named file, and pushes without force. If `main` moved since the fetch the push is rejected and
the next attempt rebuilds on the newer `main`. A file that already matches `main` makes no commit.
The runner's own checkout and index are never committed. Each staged file must be a regular file
holding exactly the generated bytes (a symlink or directory on `main` at that path is refused, never
followed). Each fetch and push is cut off after 60 s, and the step has `timeout-minutes: 15`. Only a
run on `main` publishes: each commit step's `if:` requires `github.ref == 'refs/heads/main'`, and the
script refuses any other `GITHUB_REF`.

**Why it replaced the soft-reset loop.** The old step committed in the runner's checkout, then
looped `git fetch origin main && git reset --soft origin/main && git commit && git push`. A soft
reset moves the branch but keeps the runner's whole index from its checkout, so the commit's tree
was the old checkout plus the artifact: every change merged to `main` while the run was in flight
was silently reverted, with no conflict and no failed check. It happened twice: 2026-10-02
`4bb6c39` undid `desk/cap-weight` (restored by `9a97c23`) and 2026-11-04 `d9359019` undid #35 and
#30. Concurrency groups do not prevent it: a code merge is not a workflow run. Max approved
replacing the pattern on 2026-11-04.

`tests/test_publish_artifacts.py` rebuilds the race in real repositories (a bare origin, a runner
checkout taken before a merge, the merge, then each workflow's own publish command read from its
YAML) and shows the old step reverting the merge on the same scenario.

### Rules for future workflow edits

1. A workflow that writes to git calls `scripts/publish_artifacts.sh` with explicit paths. Never
   `git commit` or `git push` in a workflow step, never commit the runner's checkout (no
   `reset --soft`, no stash/rebase), and never force-push. A new generated file is a reviewed
   addition to `ALLOWED`.
2. If adding a third workflow that uploads the DB Release asset, give it the same `concurrency: { group: data-write, cancel-in-progress: false }` block.
3. Keep at least 3 attempts and the backoff in the publisher.
4. After merging a PR, check that `main` still contains it: `git diff <merge> origin/main --stat`
   should list only bot artifact paths. A run that started before a workflow change still uses
   the workflow it started with.
5. If a scheduled run fails, investigate it as a new bug.

### Modes and validation (2026-09-06)

`refresh-data.yml` has four explicit modes — `full` (11:17 UTC daily, 00:23 UTC Tue–Sat), `news-only` (hourly at :41, lean `requirements-news.txt`), `market-only` (`requirements-market.txt`), `verify-only` — resolved by `scripts/workflow_mode.py` (an unknown cron becomes `verify-only`, never `full`). Every DB-writing run keeps `data/previous.db`, runs `scripts/validate_db.py` (integrity, tables, counts, max-date regression, mode-scoped SLA verdicts, step summary) and uploads only on `pass` + changed. Full runs publish `snapshot-latest.json` and a `validated-db` artifact; after a validated morning full run the refresh dispatches `daily-memo.yml` / `weekly-memo.yml` with its run id and they consume that artifact, refusing anything but `mode=full` (no stash/rebase anywhere). `make sync-data` pulls the Release asset locally with the same validation. Both DB writers then run a separate **"Publish the validation verdict"** step right after the DB publish step (same condition, `timeout-minutes: 1`, `continue-on-error: true`): `scripts/validation_asset.py` (stdlib) writes `publish/validation.json` `{verdict, mode, timestamp, db_sha256}` and it is uploaded with `--clobber`; a failure only leaves the verdict absent, and the DB publish step never mentions it (pinned by `tests/test_workflows.py`). Full mode also carries the Options Finder earnings cache's durable ledger (Amendment A-1, `docs/desk/EARNINGS_CACHE.md`): "Fetch earnings cache ledger" just before the cache step and "Publish earnings cache ledger" (`if: always()`) after the verdict step, both `continue-on-error`, 2 minutes, built-in `GITHUB_TOKEN` only. Its assets are immutable and sequenced: never upload them with `--clobber`, and never fold them into the DB publish step's validation gate. `weekly-memo.yml` builds the memo with `python -m src.memo` from the repo root (fix/site-audit S-06: `python src/memo.py` put `src/` on the path, the memo's `src.utils.format` import failed, and no weekly memo was built from at least Sep 7); `tests/test_weekly_memo_entrypoint.py` runs the workflow's own command.

`validate_db` judges `alert_feed` as a recomputed table (`RECOMPUTED_TABLES`): the full run rebuilds it whole, so a cleared alert moving its max date earlier, or its rows falling, is a warning. Oct 20–21 2026 a cleared VIX_shock alert (dated 2026-10-02) failed every full refresh, because the failing run never published and the baseline kept the alert. A run with no alerts empties the table (`upsert_alert_feed` always replaces it; before, it returned early and the last run's alerts stayed on screen, Codex S-03). `fred_client._download` retries five times over about two minutes: FRED's outage page is an HTTP 200 with a non-XML body, which fredapi raises as `ParseError` (Refresh Data #2308).

## Refresh-attempt status (F-3, Max 2026-11-04)

`refresh-data.yml` full runs upload `refresh-status.json` to the `data-latest` release twice: "Upload refresh-attempt status (started)" after the mode step, and "Upload refresh-attempt status (finished)" after every other step except the cutover mirror (`always()`). Both are `continue-on-error` with a two-minute timeout, use the job's `GITHUB_TOKEN` unless `DATA_RELEASE_REPO` names another repo (below), and never touch `macro_radar.db` or `validation.json`; the DB is still published only by "Publish validated DB snapshot" when validation sets `upload`. The steps are named "Upload…" because `tests/test_workflows.py` takes the first step whose name starts with "Publish" as the DB upload. No other workflow writes the status (`tests/test_refresh_status.py`). The API reads it (`api/refresh_status.py`); see `.claude/rules/api.md`.

### Which repo holds data-latest (private storage)

Every database, snapshot, verdict and refresh-status release command takes `--repo "$DATA_RELEASE_REPO"`, from the workflow-level env `${{ vars.DATA_RELEASE_REPO || github.repository }}`: unset = this repo, exactly as before. Its first run line is the token switch (the `DATA_RELEASE_TOKEN` secret only when the repo differs). The earnings ledger steps never read it. A new step that touches `data-latest` follows the same pattern, and `tests/test_data_release_repo.py` checks every `gh release` line. The cutover mirror (`scripts/mirror_data_release.sh`) runs only while `vars.DATA_RELEASE_MIRROR == 'true'`. Procedure: `docs/data/PRIVATE_STORAGE.md`.
